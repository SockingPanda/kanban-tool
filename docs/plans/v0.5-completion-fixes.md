# V0.5 Completion Fixes Implementation Plan

> **For maintainers:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Bring V0.5 from a runnable prototype to a spec-compliant local Kanban / durable work queue MVP.

**Architecture:** Keep SQLite-only and CLI-first. Repair the state machine invariants in `kanban-sqlite` service first, then expose only the required CLI parity and update docs. Every implementation task must be TDD-driven and pass independent spec + quality review before the parent merges.

**Tech Stack:** Rust workspace, rusqlite, clap CLI, SQLite migration already present.

---

## Gates

- **Pre-flight gate:** branch must start from clean `main`; key docs and `AGENTS.md` must be read before implementation.
- **Revision gate:** each task must pass spec review first, then quality review. P0/P1 findings loop back to an implementer on the same branch.
- **Pre-flight gate before merge:** parent must run `cargo fmt --check`, `cargo check --workspace --exclude kanban-desktop --tests`, `cargo nextest run --workspace --exclude kanban-desktop --no-fail-fast`, `cargo clippy --workspace --all-targets --exclude kanban-desktop -- -D warnings`, and a real CLI smoke against a temporary DB.
- **Escalation gate:** if a reviewer finds a spec/document contradiction or 3 review cycles do not converge, stop and ask the user.

## Task 1: Atomic claim and dispatch claim selection

**Objective:** Make `ready -> running` atomic and add tests proving the invariant.

**Files:**
- Modify: `crates/kanban-sqlite/src/service.rs`
- Test: `cargo nextest run -p kanban-sqlite --no-fail-fast transitions`

**TDD steps:**
1. Add failing tests for:
   - two concurrent claim attempts on one ready task result in exactly one success;
   - a claimed task always has `current_run_id`, one running `task_runs` row, and a `task.claimed` event;
   - `dispatch_once` does not claim `review` or dependency-blocked tasks.
2. Run focused test and verify RED.
3. Implement transaction-backed claim with one SQLite transaction: select/guard, CAS update, insert run, update current_run_id, insert event, commit.
4. Ensure dispatcher uses the same claim path and does not query/modify status outside the command service invariant.
5. Run focused test, then workspace tests.

**Review checklist:**
- `ready -> running` side effects are inside one transaction.
- affected_rows=0 returns conflict/dependency-blocked, not partial success.
- No direct status write bypasses service transition semantics.

## Task 2: Dispatcher MVP completion: promotion, heartbeat, retry policy

**Objective:** Match `docs/DISPATCHER_SPEC.md` MVP: reclaim expired, promote due/todo, claim, run with heartbeat, finish by success/failure policy.

**Files:**
- Modify: `crates/kanban-sqlite/src/service.rs`
- Modify: `crates/kanban-cli/src/main.rs` only if new options are needed
- Test: `cargo nextest run -p kanban-sqlite --no-fail-fast dispatch`

**TDD steps:**
1. Add failing tests for:
   - `dispatch_once` promotes scheduled/todo tasks that are eligible before claim;
   - `dispatch_once` heartbeats during a long-running command so `claim_expires_at` extends;
   - failed command with ready/retry policy increments `retry_count` and eventually blocks at `max_retries`;
   - reclaim expired respects `max_retries`.
2. Run focused tests and verify RED.
3. Implement promotion pass and write `task.promoted` events.
4. Implement dispatcher heartbeat wrapper for spawned worker commands.
5. Implement retry/max_retries handling for failure and reclaim.
6. Run focused test, then workspace tests.

**Review checklist:**
- `review` is never claimed.
- `blocked -> ready` is recomputed, never blindly set.
- Long-running workers do not lose claim just because command blocks.

## Task 3: Dependency guards, CLI parity, and V0.5 docs accuracy

**Objective:** Close remaining V0.5 spec gaps or explicitly document out-of-scope CLI items.

**Files:**
- Modify: `crates/kanban-sqlite/src/service.rs`
- Modify: `crates/kanban-cli/src/main.rs`
- Modify: `docs/V0.5.md`
- Test: `cargo nextest run -p kanban-sqlite --no-fail-fast dependencies`

**TDD steps:**
1. Add failing tests for:
   - adding an incomplete parent to a running child is rejected unless an explicit force path exists;
   - CLI update can set/clear `scheduled_at` and `due_at` if service supports them;
   - `done` and `complete` aliases both work if V0.5 claims CLI parity for complete.
2. Run focused tests and verify RED.
3. Implement the smallest service/CLI changes needed.
4. Update `docs/V0.5.md` so claims match actual V0.5 scope; label comments/attachments/labels/board/server/doctor as out of scope unless implemented.
5. Run focused test, then workspace tests.

**Review checklist:**
- Docs do not overclaim.
- CLI commands either match V0.5 claims or are explicitly marked future work.
- Dependency invariants match `docs/STATE_MACHINE.md`.

## Final Integration Review

After all tasks pass, dispatch two fresh reviewers:

1. **Spec reviewer:** compare implementation against `AGENTS.md`, `docs/STATE_MACHINE.md`, `docs/DISPATCHER_SPEC.md`, `docs/CLI_SPEC.md`, and `docs/V0.5.md`. Return P0/P1/P2.
2. **Quality reviewer:** review code quality, transaction safety, SQL correctness, error handling, tests, and security risks.

Only after both approve may the parent run final verification, squash merge to `main`, delete branch, and re-run verification on `main`.
