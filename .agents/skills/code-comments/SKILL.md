# 源码注释

把调用者需要依赖、但仅看签名或实现不容易理解的信息放在代码附近。遵循仓库的[文档规则](../../../docs/documentation.md)：普通函数可能只需一句摘要，也可能无需新增注释；不要求每个函数填满一套章节。

## 先核对事实，再决定写什么

围绕本次改动阅读实现、相关调用者与必要测试，确认职责、状态归属和真实失败路径。优先说明以下信息中确实有用的部分：

- 能力与边界：为什么存在，负责到哪里，哪些职责属于调用者。
- 调用契约：输入语义、状态转换、替换或追加、清除值含义、何时算完成。
- 特殊约束：事务边界、幂等性、并发、资源生命周期、失败后保留什么，以及兼容行为的理由。
- 正确用法：仅在类型和摘要不足以避免误用时提供示例。

已有测试通过不等于注释中的所有保证都成立。例如，写“持久化后完成”前，要确认等待的是事务提交，而不只是发起写入。证据不足时说明真实限制，不把计划、调用者假设或当前巧合写成稳定保证。

实现变化时同步修正或删除过期说明。按[根契约](../../../AGENTS.md)，新增或修改的项目自有注释以简体中文为主，命令、路径、API 和字段保留 literal；不批量翻译无关注释，也不扩大为无关代码的整理。

## TypeScript：使用标准 TSDoc

对 API、接口或模块的文档说明使用 `/** ... */`。局部实现理由用附近的普通注释，不必强行套文档标签。

| 信息                                   | 承载方式                                                 |
| -------------------------------------- | -------------------------------------------------------- |
| 这是什么、提供什么能力                 | 首段摘要                                                 |
| 设计理由、职责边界、调用者可依赖的规则 | 正文或 `@remarks`                                        |
| 参数、返回值及异步完成时机             | 按需使用 `@param`、`@returns`                            |
| 实际抛出异常或 Promise 拒绝的条件      | 按需使用 `@throws`；返回错误值的语义写在正文或返回说明中 |
| 容易误用的调用方式                     | `@example`                                               |
| 已有符号之间的关系                     | 可解析的 `{@link SymbolName}`                            |

只使用生态已有标签，不增加 `@why`、`@contract` 等自定义标签。不要重复类型系统已经清楚表达的信息，或把标签齐全当作质量目标。

需要模块整体背景时，用 `@packageDocumentation` 标记文件的首个注释块，放在 import 之前，并保留已有版权和许可声明。把共用背景集中在这里，不复制到每个导出函数。

下面只演示注释写法，不要求仓库实现这个接口，也不把单迭代规则推广到其他关联：

```ts
export interface TaskCycleService {
  /**
   * 替换任务当前所属的迭代。
   *
   * @remarks
   * 一个任务至多属于一个迭代。本操作替换该归属；
   * 不追加第二个迭代，也不管理多对多的模块归属。
   *
   * @param taskId - 待更新的任务。
   * @param cycleId - 目标迭代；null 表示清除当前归属。
   * @returns 归属变更持久化后兑现的 Promise。
   */
  setCycle(taskId: string, cycleId: string | null): Promise<void>;
}
```

### React：说明状态与副作用的归属

组件注释优先回答：受控还是非受控，状态由谁持有，回调何时触发，保存、订阅或其他副作用由谁负责。只有影响使用的焦点、取消或卸载行为才需要记录；不要复述 JSX、图标、样式或每次 render 的步骤。

下面的回调约定只有在实际组件遵循它时才能采用：

```ts
/** 受控迭代选择器的属性。 */
export interface CyclePickerProps {
  /** 父组件持有的当前选中值；null 表示未选择迭代。 */
  value: string | null;
  /**
   * 用户选择或清除迭代后，请求父组件更新选中值。
   *
   * @remarks
   * 外部修改 value 不触发此回调。父组件负责持久化和错误处理；
   * 选择器本身不保存归属。
   */
  onChange: (cycleId: string | null) => void;
}
```

## Rust：使用 rustdoc 的现有约定

模块背景使用 `//!`，条目文档使用 `///`，局部实现理由使用 `//`。ownership、模块组织与 owner guide 的 include 方式遵循 [style](../style/SKILL.md)。首段提供摘要，其余按实际需要展开：

- `Design`／`Boundaries` 可用于模块职责与设计理由，不要求每个条目都有。
- `Errors` 说明返回错误的条件和副作用；`Panics` 说明真实 panic 条件，不为了填表编造失败路径。
- `Safety` 用于 unsafe API 的调用者安全义务；普通安全函数不添加空的 Safety 章节。
- `Examples` 用于有帮助的用法；适合时使用可运行的 doctest，不用 `ignore` 掩盖失效示例。
- 涉及服务或资源边界时，按需说明事务、幂等性、并发和资源释放保证；不假设所有 Rust 模块都是服务。

## TODO 与长期说明分开

使用代码 TODO 承接或委派细节时，写清待实现行为、相关输入输出、必须保留的约束和完成条件；信息量随任务复杂度调整。任务归属、进展和完整执行清单仍放在 Kanban，不在注释里再维护一份。

TODO 表达尚未完成的工作，不能在 TSDoc／rustdoc 中同时宣称已经支持。实现完成后移除已兑现的 TODO，只保留仍有长期价值、且与实现一致的说明。不在注释中保存临时 agent 对话、运行日志或模型分工历史。

## 使用现有检查，并准确描述其范围

先按 [check](../check/SKILL.md) 和根 [justfile](../../../justfile) 选择与当前改动匹配的检查：

- 修改 rustdoc、include 或公开 Rust 文档契约时运行 `just docs-check`，同时修改代码时补对应 owner gate。会写 Cargo target 的检查通过现有 recipe 的 build lock 执行。
- TypeScript／React 改动按影响面运行 `just web-typecheck`、`just web-lint` 等现有检查。当前 [Web ESLint 配置](../../../apps/web/eslint.config.js)未接入 TSDoc 语法检查，仓库也未提供独立的 TypeDoc 文档 gate；不能把这些命令通过表述为 TSDoc 标签、符号链接或文档覆盖已经通过验证。
- 只修改本 skill、根路由或 Markdown 指南时，按对应影响运行 `just docs-structure-check`、`just agents-check` 和 `just diff-check`；它们不执行这里的 TypeScript 示例，也不验证业务保证。

不要为了使用 skill 扩大为全仓库文档补齐、修改检查范围、增加检查依赖或添加自定义标签。语法、链接、覆盖率和示例执行都不能替代业务说明的真实性核对；发现注释与实现冲突时，按本次授权解决或明确指出，不为了让注释成立而暗改业务行为。

只有跨组件且难以放在源码附近理解的稳定设计理由，才按仓库规则写入内部文档；使用源码链接，避免复制同一份契约。
