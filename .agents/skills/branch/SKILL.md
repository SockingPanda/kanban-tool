# 分支与本地合并

在用户已授权的目标内完成分支操作。用户明确指令优先于本 skill 的指南；同一目标内已有授权持续有效，不重复确认。只在缺失信息会改变分支归属、操作范围或共享历史时询问，并说明具体分歧。

## 层级与合入方向

`vx` 是版本分支的统称，例如 `v4`，不是要创建的字面分支名。

| 分支 | 创建基线与职责 | 合入目标 | 合并方式 |
| --- | --- | --- | --- |
| `main` | 当前稳定版 | — | — |
| 版本分支 | 明确的稳定版基线，承载该版本开发 | `main` | `git merge --no-ff <版本分支>` |
| 开发分支 | 对应版本分支，承载一个开发目标 | 所属版本分支 | `git merge --no-ff <开发分支>` |
| 派生子分支 | 直接父开发分支；更深层派生沿用此规则 | 直接父分支 | `git merge --ff-only <子分支>` |

合并命令在目标分支执行。开发分支逐层回到所属版本，不直接合入 `main`；子分支先回到直接父分支。存在待合入提交时，`--no-ff` 保留合并节点；源提交已经全部包含在目标中时报告无需操作，不制造空合并。

## 识别与创建

- 核对当前分支或 detached HEAD、工作区与 index 改动、worktree 占用、源与目标 SHA，以及父分支和所属版本。已有 merge/rebase 未结束时先识别其归属，不叠加新操作。
- 优先采用用户指定关系、Kanban 任务记录和分支创建证据。Git 拓扑用于核验；名称、共同祖先或没有 upstream 都不能独立证明父分支或共享状态。归属不明时先只读调查，再询问仍缺失的决定。
- 新建开发分支默认使用 `codex/` 前缀，用户指定名称优先。新版本的稳定版基线必须明确，不从多个 `v*` 分支中自行选择最大版本。detached HEAD 只是当前检出状态，不能代替基线决定。
- 创建、切换可在已授权目标内执行。保护既有改动，不自动 stash、reset 或覆盖文件；目标由其他 worktree 检出时核对该工作区及任务归属，不强制抢占或移动其分支引用。
- 在对应 Kanban 任务记录分支名、创建基线 SHA、直接父分支、所属版本和合入目标，供后续操作恢复；不新增另一份分支配置事实源。

## 合并与快进整理

普通“开发完成”不自动授权合并。用户明确指定的本地合并授权包含必要的 merge commit，无需再次请求 `$commit` 授权；普通代码提交交给 [commit](../commit/SKILL.md)。

合并前回读源与目标、检查差异并核对 [check](../check/SKILL.md) 中与影响面匹配的验证证据。测试依据绑定实际提交或 diff；整合或冲突解决改变内容时补相应验证，不把合并前的测试当作合并结果已通过。

子分支无法快进时：

- 合并授权包含对确认未共享子分支的 rebase，再以 `--ff-only` 合入父分支。结合创建与推送记录、用户说明及当前引用核实；缺 upstream 或本地 remote-tracking ref 不足以证明从未共享。
- 只重放子分支自己的提交，先明确分叉边界和提交范围；必要时使用 `git rebase --onto <父分支> <已核实的旧基线> <子分支>`。不改写父开发分支、版本分支或 `main`，不静默展开或丢弃已有合并拓扑。
- 已共享、共享状态不明或重放范围无法确认时，报告分叉、拟改写范围和影响，等用户决定；不能退回普通 `git merge` 绕过 `--ff-only`。
- 冲突在现有目标内且语义明确时自行解决；需要新产品决定或无法可靠确定内容时保留现场，说明冲突文件、当前操作和待决定事项。

## 回读与停止

操作后核对当前分支、目标 SHA、父提交及工作区状态；`--no-ff` 的新提交应以合并前目标为第一父提交、源为第二父提交，快进后的目标应等于已核实的源 SHA。记录实际操作、验证和剩余问题后停止。

本 skill 不自动删除分支、push、开 PR、发布或改写远端历史；远端操作需要另行授权。若本 skill 的具体规则导致暂停或偏离用户目标，链接本文件并引用该规则，区分明确要求与自己的推断。
