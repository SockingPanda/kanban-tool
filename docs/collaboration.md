# Agent 协作与变更边界

本指南规定跨任务的协作方式。当前代码拓扑见 [架构](architecture.md)，操作授权与产品不变量见
[根契约](../AGENTS.md)。任务分支、基线、进行中的计划和验证结果留在任务记录，不在仓库内建立第二套任务数据库。

## 开始一个任务

先确认用户可观察的结果、验收证据、非目标和停止条件。读取根契约后，只读取相关 owner 的约定、
调用链与测试。不要把所有 skill 和所有指南一次性放入执行上下文。

在任务记录中保留起点 SHA、直接父分支、版本归属、可修改路径、需要协调的共享入口、验收方式和
已知限制。任务可以由一个 agent 完成设计、实现、测试和文档。需要并行时，按职责分开工作区；
一个 worktree 对应一个写入者。同一目标下已经明确的授权和产品决定无需反复询问。

公开契约、数据库迁移入口、应用装配和依赖锁文件属于共享入口。每次集成由一个执行者协调这些文件，
其他 agent 交付所需差异与依据。该职责只针对当前集成，不新增永久的角色、权限或分支登记系统。

## 先明确契约，再并行实现

新增能力先确认身份、命令与返回值、错误码、并发校验、持久化责任和刷新语义。已有事实必须由原 owner
继续持有。纯数据可扩展性不得绕开任务的状态机、claim、lease、run 或事务规则。

各入口共享 application service。协议由 Protobuf、catalog 与生成工具持有，组件消费 application
接口，Host adapter 负责传输。功能实现不能为绕过接口缺口偷偷增加一条 HTTP/数据库写路径。
进程内工作由现有 service 接口完成；不为保持表面统一而增加不必要的回环 RPC。

跨功能契约变化完成后，通知其他执行者使用明确的契约版本或提交。无需等待所有局部实现完成后才发现
字段、错误与事务边界不一致。实现中的新决定记录到任务，长期成立的跨模块取舍再进入 ADR。

## 文件归属与生成物

功能内部可以继续按现有模块拆分，公共出口尽量小。迁移目录、机械重命名与业务变化分开；只有确实能
减少长期依赖或职责混杂时才新增 crate。大文件的行数是调查线索，不能独立证明需要拆 crate。

生成源由原 owner 修改，生成物由该 owner 的命令产生。不要让多个 agent 手工合并生成文件，再保留与之
不一致的源文件。依赖锁文件由集成执行者在已核对的版本与工具链下统一生成和检查。

文案由对应语言目录/翻译系统持有；错误码、数据库键、类型身份和协议字段保持稳定 literal。展示语言
不得改变持久化身份。附件、模块、迭代等功能增加文案时，使用已有翻译 owner，不另存 locale 状态。

## 旧交付包的使用

旧包首先是有基线的代码与证据。记录其 SHA、变更文件和测试环境，再与当前 owner 源码比较。
旧基线通过的测试只能证明旧基线上的结果。完整文件覆盖、字符串替换或旧迁移序号不能代替语义合并。

发生共享文件冲突时，由集成执行者核对当前调用链与不变量，重新接线并验证。不要为了让旧脚本运行而
降低其基线检查、用新 SHA 替换旧预期 hash，或恢复已退出的传输层。无冲突的文本合并也需要检查语义。

## 构建资源

所有会写 Cargo target 的命令使用现有 `scripts/cargo-build-lock.sh`。本地机器为该仓库约定一个稳定的
`KANBAN_CARGO_TARGET_ROOT`，同机所有 worktree 共用它；不要按任务、分支或 agent 创建 target。
已配置的开发环境保持原配置。新机器由环境设置持有该值，不把某位开发者的绝对路径复制进 CI。

CI 在同一个 runner 内为所有 recipe 设置相同的 target root。锁只串行化 Cargo target 写入，不串行化
源码、迁移、锁文件或任务状态。并行源码编辑仍需独立 worktree 和明确写入者。

现有 wrapper 依赖 Linux 的 flock、setsid、/proc 与 GNU 工具。Linux/WSL 是这组脚本的执行环境。
项目能够构建某个平台的产物，不等于这组构建脚本已经支持该平台的原生命令行。

## 验证与交付

以当前 `justfile` 选择最小充分验证。纯文档与导航先运行 `just docs-structure-check`；skill 与根契约
同时运行 `just agents-check`。涉及 Rust 文档示例、include 或公开 Rust 契约时保留 `just docs-check`。
`just repo-check` 组合仓库结构检查，它仍需编译 xtask，不是无编译成本的文本检查。

验证记录绑定实际提交或 diff，区分 passed、failed、blocked、not_run，并写明环境和限制。新测试已编写、
静态分析通过、模拟数据通过、真实 Host 通过各自独立。合并改变内容后，重新验证受影响路径。
`git diff --check` 不覆盖未跟踪文件；交付前还需核对新增文件。

默认由同一执行者完成实现、必要测试、文档、自检和交付。独立审查仅在用户明确要求时启动，不因
日期、版本、风险或任务完成自动安排 reviewer。发现问题由执行者定位、修复并补充必要验证。

交付包含变更范围、行为影响、验证证据、未完成项和下一位执行者需要的最小上下文。一次性交付报告和
历史验证记录放在任务或发布附件；active 文档只保留当前使用方式与持续成立的边界。

## 停止与恢复

不覆盖其他 worktree 的 dirty work，不擅自 stash、reset、切换他人的分支或更新远端。普通代码提交、
本地合并与远端操作分别遵循各自授权。遇到不明确的产品决定，保留已有成果和具体冲突，不猜测数据语义。

代码回退与数据回退分别计划。不能用 git revert 代替数据库恢复；迁移验收先使用可丢弃数据库副本。
没有恢复验证的备份只是一份备份文件，不能报告为已证明可恢复。
