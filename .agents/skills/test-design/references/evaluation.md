# 触发复核与演进

## 如何使用

修改 skill 的触发描述或决策规则时，用下表检查是否仍能导向正确选择。小改动检查相关行；
改变范围或原则时检查全部。它是人工／当前执行 agent 的复核题，不是新增 CI、模型评测服务或
必跑的产品回归。未实际调用模型就写“静态复核”，不能声称隐式触发已实测。

| 场景提示 | 预期选择 | 应避免的错误 |
| --- | --- | --- |
| 新增字段校验；已有同类边界表 | 使用本 skill，在最小 owner 表补行与期望 | 从创建项目开始复制一条完整 E2E |
| 每个 fixture 前都跑同一整库导入 | 对照断言后拆格式检查，完整流程保留一次 | 只换 Docker、OnceCell 或扩大并发 |
| 删除测试只查询早已不存在的词 | 先补删除前存在与删除后不存在的观察 | 原断言不变，仅缩小数据或改名 |
| 压缩随机状态机测试 | 限制预算，保留独立模型、seed 与最小反例 | 每个样本建整库，或删除关键反例 |
| 中断恢复很慢，希望删掉 | 核对独有故障边界，缩小必要样本而保留证明 | 隐藏、ignore 或用 happy path 冒充恢复 |
| 多个独立并发契约共用活跃库 | 保留隔离与真正竞争，需要时复制不可变准备数据 | 为省初始化顺序共享状态、让测试互相依赖 |
| 只是私有函数改名，行为不变 | 现有行为契约足够时不新增测试；用 check 验证 | 为每个 rename 添加源码文本匹配测试 |
| 只问“这次应该运行哪个 just recipe” | 使用 check；本 skill 不是必选 | 无故开始测试体系重构 |
| 只改 README 措辞 | 使用 prose／docs；不触发本 skill | 自动新增回归或安排 reviewer |
| 合并测试后旧过滤器选中零用例 | 同步过滤器并核对实际选中数 | 将零用例或仅默认 feature 当作完整验证 |
| 两次运行缓存、范围不同 | 分开报告原数据，说明不可比 | 从总耗时差宣布稳定加速百分比 |
| 多个便宜测试共享 helper 但契约不同 | 保留独立行为；可容忍少量重复来保持可读 | 为减少条数强行合成巨型旅程 |

## 成本优化的反例复核

以下延续上表；只复核本次改动涉及的行，不自动增加产品测试入口。

| 场景提示 | 预期选择 | 应避免的错误 |
| --- | --- | --- |
| 大型测试程序只被用来验证进程身份 | 换小型真实子进程，保留身份／参数／路径／哈希负例与清理 | 伪造哈希、改成纯 mock，或声称生产校验加速 |
| 首次导入与重放合并，断言都放到最后 | 恢复首次观察点，再验证重放不改变事实 | 用第二次修复后的结果替第一次通过 |
| 替换重试复用自己导出的快照 | 使用 A/B 与 A′/C 区分字段恢复、删除和新增 | 只改标题，丢掉目标独有记录移除的证明 |
| 两个排序列使用相同值分布 | 修改样本，使互换列的错误至少一项失败 | 用同一查询的重复性代替正确顺序 |
| 关闭测试缩短私有等待，生产默认未变 | 仍证明目标路径，区分许可的 reaper outcome 与无关 Err | Drop 清理成功便接受任意 shutdown 错误 |
| 子进程忽略信号已在 pre-exec 安装 | 接受这一准备边界，按实际证明需要观察后续行为 | 为“规范”再添加无必要的 ready 文件 |
| 首请求一秒超时，第二请求应返回 busy | 保证首调用仍占用 permit 的重叠窗口；分开验证超时映射 | 接受 TCP 后假定所有进程一定及时获得调度 |
| stop 已取消并 join 所有相关任务 | 可去掉为该退出而设置的固定尾部等待 | 把仅 send(stop) 也视为任务已退出 |
| 分页数据改为单事务批量插入 | 确认读取发生在提交后，保留真实页上限／尾批 | 顺手改变被测逐提交可见性或崩溃边界 |
| schema validator 和目录扫描结果复用 | 单次命令、来源对应、全量与负例仍检查；评估内存 | 永久复用旧快照或允许 zip 静默漏检查 |
| 一个修改后续已撤回，曾有单项好成绩 | 按最终净 diff 统计，保留退出原因 | 把中间提交仍算成当前收益 |
| test build 与 Clippy 已覆盖前置 check | 由 check 核对 targets／features，测整条门禁 | 直接扣除旧阶段秒数，或顺手删除独立 check 入口 |

## 新经验进入 skill 的条件

先保存实现／diff／日志证据及复现条件到本次任务，再判断是否可推广。区分：产品不变量、设计
默认、工具限制、一次性工作区故障。只有前三者中确有长期价值的部分进入本 skill；耗时、条数、
任务状态、提交进度与机器配置不要进入正文。

修订时说明“此前规则在什么条件失效、新规则适用于哪里、反例是什么、应替换哪一段”。
优先替换、合并或收窄已有规则；不要为同一个思想增加多份说明。若真实证据推翻原假设，明确
改掉旧假设，而不是在末尾加一条例外后保留互相矛盾的指令。

在当前授权的文件修改范围内维护这些文件；commit、push 与发布仍遵循根 Git 边界。本 skill
不能自行给执行 agent 增加部署、全仓重构或后台工作的权限。复核不需要额外开启 reviewer。

## 结构检查与行为复核的区别

`AGENTS.md` 路由、技能目录、frontmatter 和 UI metadata 由现有 `agents-check` 接线；它验证
结构，不验证模型真的理解了设计原则。修改后用 `$check` 选择当前存在的窄 gate。
不要新增逐句匹配 skill 文案、测试名配额或强制新测试数量的 guard 来替代理解。

当前任务的交付说明可以用一小段或一张表表达“契约 → 原证明 → 新证明 → 验证状态”。不在
仓库维护第二份全量测试库存；未来重新检查以当前代码、实际选中用例和执行结果为准。
