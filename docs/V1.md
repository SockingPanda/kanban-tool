# V1 Local Release Notes

V1 is the local-first release hardening milestone for the SQLite-backed Kanban/work queue. It includes the localhost API, desktop-oriented operator surfaces, dispatcher loop support, run/retry visibility, and local maintenance commands on the same command service used by `kb`.

## Implemented scope

- `kanban-server` crate with Axum router construction via `build_router(AppState)`.
- `kb serve` command.
- SQLite-only storage and idempotent database initialization when serving.
- Localhost default bind: `127.0.0.1:8721`.
- JSON success envelope: `{ "data": ..., "meta": ... }`.
- JSON error envelope: `{ "error": { "code": ..., "message": ... } }`.
- Actor resolution for mutating HTTP routes: body `actor`, then `X-KB-Actor`, then server default actor.
- Comments API, run detail/log APIs, stats API, and maintenance doctor/checkpoint APIs.
- `kb dispatch` foreground loop with worker profile config.
- `kb run show`, `kb run logs`, `kb stats`, `kb backup`, `kb export`, `kb import`, `kb checkpoint`, and `kb vacuum`.
- Expanded `kb doctor` checks for integrity, migration state, stale claims, orphan running runs, dependency cycles, archived dependency edges, missing run logs, and executable status invariant violations.

## Serve command

```bash
kb serve
kb serve --host 127.0.0.1 --port 8721 --db /tmp/kb.db --actor local-dev
kb serve --search-sync-interval-ms 0
```

Defaults:

- Host: `127.0.0.1`
- Port: `8721`
- DB: the normal CLI default data path unless `--db` is provided
- Actor: OS username/default CLI actor unless `--actor` is provided
- Search sync interval: `5000` ms when built with `tantivy-backend`; `0` disables

`kb serve` rejects non-loopback hosts; use `127.0.0.1` or `::1`.
With `tantivy-backend`, `kb serve` starts one prompt background search index sync
attempt after binding and continues at the configured interval. Without the
feature, the flag is accepted and no background index task starts. Search routes
continue to report stale/fallback metadata and use SQLite fallback whenever the
derived Tantivy index is behind, missing, or unusable.

## SSE event stream behavior

V1 implements `GET /api/v1/stream/events` as a finite snapshot stream. It reads matching rows from `task_events`, emits them as SSE frames, and closes the response.

Example frame:

```text
event: task.created
id: 123
data: {"id":123,"event_id":"e_...","task_id":"t_...","kind":"task.created","payload":{}}
```

Query behavior:

- `board` defaults to `default`.
- `board` accepts slug or id; archived board event history remains readable.
- `after` defaults to `0` and returns events with DB id greater than `after`.
- `limit` defaults to `100` and is capped at `1000`.
- SSE `id` is the monotonic `task_events.id` database id.
- Invalid query parameters return the normal JSON error envelope before an SSE stream is opened.

Continuous polling/long-lived dispatch from this endpoint is intentionally deferred; clients that need updates in V1 should reconnect or periodically call `GET /api/v1/events`.

## Out of scope for V1

- Browser Web UI bundle, drag/drop frontend, or static asset server.
- Remote auth, users, RBAC, teams, tenants, or SaaS collaboration semantics.
- Labels and attachments APIs beyond existing schema/storage placeholders.
- HTTP backup/export/import endpoints. Backup/export/import remain CLI-only.
- Persistent dispatcher service supervision.
- A long-lived SSE dispatcher with blocking waits for future events.
