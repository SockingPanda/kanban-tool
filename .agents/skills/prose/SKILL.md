# 项目文案与长文

## 行为契约

能力：把项目事实写成清楚、可行动且可验证的中文用户文案或长篇文档。

触发：

- 新写或重写 README、`docs/*.md`、ADR、操作指南、CLI/HTTP/Desktop 的用户可见错误、帮助、状态提示或 Markdown 示例。
- 用户要求改进文案、文档结构、措辞、解释顺序或示例。

不触发：

- 只决定应读或应改哪个事实源，使用 `$docs`。
- Rust、Cargo、模块或测试组织，使用 `$style`。
- 选择和运行检查，使用 `$check`；创建提交，使用 `$commit`。
- 只改内部日志、开发者注释或不面向用户的字符串时，按普通编辑处理，不强行加载本 skill。

成功标准：

- 开头直接说明当前结论、适用范围和读者下一步。
- 结构从最小可用路径进入高级细节；重复定义改为短说明加链接。
- 示例使用当前命令、字段和状态，能由当前代码、help、测试或规范核对。
- 文档描述当前产品，不把撤销的方案、迁移过程或 roadmap 写成现行行为。
- 错误与状态提示说明发生了什么、用户能做什么，并保留稳定 machine code 与字段名。

硬约束：

- 项目自有说明以简体中文为主；命令、路径、crate、API、JSON 字段、枚举、库名和协议名必须保留精确原文。
- 中文和 Unicode 可以出现在 prose。代码块、shell、TOML、JSON、schema、CLI 输出等机器语法必须服从 parser 的精确字符要求；不得全局机械改成 ASCII，也不得把 ASCII-only 当作本项目文档契约。
- 不凭记忆制造接口、字段、recipe、状态或已实现能力；不确定时先交给 `$docs` 选择事实源。
- 不复制一份已有 canonical 定义来形成第二个权威；引用 `docs/SPEC.md`、`docs/ARCHITECTURE.md`、`docs/API_SPEC.md` 等唯一来源。
- 不把 human-readable 文案当成稳定错误判定接口；CLI、HTTP、MCP 和 Desktop 继续依赖统一 error code/typed contract。
- 不用含混标题、过时穷举表或“过去是 A、现在是 B”的叙事冒充当前规范；历史只链接 ADR、migration note 或 Git history。

决策规则：

- 如果读者尚未完成最小操作，先写最短可运行路径，再链接高级配置、边界和故障排查。
- 如果内容已有另一份规范完整解释，只保留定义、影响和链接，不复制整段示例。
- 如果示例不能由当前证据验证，标为待核对并停止扩写，不用猜测填空。
- 如果只是代码格式或 Unicode 偏好而不影响语义，采用项目可读性优先的选择；不要为了风格批量改无关文档。

质量标准：

- 事实准确、范围清楚、读者可行动、链接可追溯、示例不过时、段落和标题易扫描。
- 默认使用直接、简洁的语言；避免不必要的英文改写、华丽措辞和重复背景。

偏好：

- 每个 Markdown 段落尽量保持为一个逻辑段，便于审阅；可按中文阅读和 diff 需要换行。
- 优先 ASCII 句法字符（如代码中的 `->`），但不牺牲中文、Unicode 语义或现有项目约定；避免 em dash 是偏好而非硬约束。

受保护的自主空间：

- 可自行选择标题数量、表格、列表、流程图、段落长度、中文/英文比例和叙事顺序。
- 可根据受众决定先给例子还是概念、是否拆分页面，以及哪些细节应链接而非展开。

非目标：

- 不决定文档的 canonical placement 或同步矩阵；不编辑生成 bundle 代替源文档。
- 不因一次文案偏好创建全局写作模板，不要求公开 hidden reasoning 或固定标题数量。

## 验证案例

- 典型触发：为 `README.md` 补充当前 `kanban serve` 使用路径，并核对命令与字段。
- 边界：在中文段落中保留 `ready -> running`、`t_...` 和 JSON fence；机器片段可解析，中文说明不被 ASCII 规则破坏。
- 失败回归：拒绝把未迁移能力或旧 fallback 写成当前可用功能，并指出待核对事实。
- 近似误触发：用户只问“哪个文档应同步”时路由 `$docs`，不产出长篇 prose。
- 自由度：同一当前 API 可用表格或分段指南表达，只要结论、字段和链接都正确。

完成长文后，把文档落点和事实源交给 `$docs`，把实际检查交给 `$check`。
